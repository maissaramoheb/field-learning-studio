# Daily Field Debrief Studio Guide (v0.9 Phase 5)

## 1. Overview & Purpose

Field Learning Studio v0.9 Phase 5 introduces the **Daily Field Debrief Studio**—a dedicated, local-first reflective sensemaking workspace for evaluators, MEL practitioners, researchers, and field teams.

In rigorous field practice, high-quality learning is not produced by running algorithms over raw notes at the end of a mission. It is produced through **disciplined, timely end-of-day sensemaking** while observations, tensions, and surprises are fresh in the minds of the field team.

The Daily Field Debrief Studio bridges the critical methodological gap between **raw evidence collection** and **structured synthesis**, helping practitioners move systematically from:

$$\text{Messy Field Reality} \longrightarrow \text{Structured Evidence} \longrightarrow \mathbf{\text{Daily Sensemaking}} \longrightarrow \text{Targeted Inquiry} \longrightarrow \text{Validated Findings}$$

---

## 2. Conceptual Foundation: Why Daily Debriefs Matter

Field missions frequently suffer from two common failure modes:
1. **Premature closure / Confirmation bias**: A team forms an early impression on Day 1 and selectively notices confirming evidence during subsequent days while ignoring disconfirming signals.
2. **Post-mission reconstruction loss**: Subtleties, contradictions between informants, researcher discomforts, and unvoiced assumptions are forgotten by the time formal reporting begins weeks later.

The Daily Debrief provides an intentional space to interrogate the data collection process daily through structured methodological prompts:
- **Surprises**: Unanticipated events or candid disclosures that challenge preconceived expectations.
- **Patterns**: Recurring operational themes emerging across different respondents.
- **Contradictions**: Direct tensions between official accounts (e.g. registries, administrative reports) and field reality.
- **Shaken Assumptions**: Programme theory-of-change causal links that may not hold true in practice.
- **Reflexivity & Bias**: Conscious reflection on interviewer framing, presence effects, fatigue, or translation nuances.
- **Missing Perspectives**: Systematic identification of stakeholder pockets or vulnerable subgroups not yet consulted.
- **Emerging Hypotheses**: Working theories formulated to guide tomorrow's inquiry without being treated as validated claims.
- **Tomorrow's Action Priorities**: Concrete, discrete field tasks to probe anomalies, follow up contradictions, or consult missing groups.

## 3. Entity Model & Schema

The debrief entity is defined in `src/lib/types.ts`:

```typescript
export interface DailyDebrief {
  id: DailyDebriefId;                // Human-readable ID (e.g. "DBR-001")
  studyId: StudyId;                  // Scoped to target study
  date: string;                      // ISO Date "YYYY-MM-DD"
  siteIds: string[];                 // Multi-site support: [] = study-wide, or array of site IDs
  attendees: string[];               // Participating field team members
  whatSurprisedUs: string;           // Required: Unanticipated observations or dynamics
  whatRepeated: string;              // Required: Patterns heard across encounters
  contradictionsObserved: string;    // Narrative divergence reflections
  shakenAssumptions: string;         // Assumptions questioned
  potentialBiases: string;           // Team/researcher reflexivity reflections
  missingPerspectives: string;       // Pockets/groups not yet consulted
  emergingHypotheses: string;        // Working theories (strictly non-findings)
  tomorrowPriorities: string[];      // Discrete actionable inquiry priorities
  linkedSourceIds: SourceRecordId[]; // Linked source records from same study
  linkedEvidenceIds: EvidenceEntryId[]; // Linked evidence observations from same study
  createdAt: number;                 // Epoch ms
  updatedAt: number;                 // Epoch ms
}
```

## 4. Strict Architectural Boundaries & Invariants

To maintain product integrity and prevent evidence contamination, Phase 5 establishes four non-negotiable architectural boundaries:

### Boundary 1: No `ValidationStatus` on Debriefs
A Daily Debrief is an **internal methodological log and reflexivity journal**, *not* a donor-facing claim or evidence observation. It does not possess a `ValidationStatus` (`Draft`, `Needs Review`, `Validated`, `Rejected`). It is saved directly by the field team to record their honest thought process without needing formal donor clearance.

### Boundary 2: Non-Mutation Invariant for Evidence
Linking an Evidence item (`EV-*`) or Source record (`SRC-*`) to a debrief is strictly referential:
- It **NEVER** mutates the Evidence record's `validationStatus`.
- It **NEVER** bumps the Evidence record's `revision`.
- It **NEVER** requires re-validation of previously validated evidence.
- It **NEVER** alters `revalidationRequired`.

### Boundary 3: Contradiction Independence
Notes recorded in `contradictionsObserved` are qualitative sensemaking reflections. They **NEVER** automatically write to or modify `EvidenceEntry.contradictionIds`. Formal evidence contradiction mapping remains a separate, deliberate human analytical act within the Evidence Matrix.

### Boundary 4: Emerging Hypothesis Isolation
Notes recorded in `emergingHypotheses` are working theories to focus future inquiry.
- They are **NEVER** automatically promoted into `Finding` or `Recommendation` records.
- They do not appear in the final Learning Brief export.
- The UI renders a prominent, persistent warning banner:
  > **Boundary Guardrail**: Emerging hypotheses are internal working interpretations to guide subsequent fieldwork, **NOT validated findings**. They are not promoted automatically into the formal evidence base or learning brief.

### Boundary 5: Traceability Drawer Suppression
When inspecting a `DBR-*` record in the Traceability Drawer:
- The linear `Source-to-brief path` (`TraceChain`) is **SUPPRESSED**, because debriefs are contextual metadata rather than steps in the formal `SRC → EV → FND → REC` evidentiary claim chain.
- The drawer displays the debrief's metadata, full reflection profile, safeguard warning note, and clickable links to all referenced Sources and Evidence.
- Clicking a linked Evidence item inside the drawer smoothly transitions the drawer to inspect that Evidence item and reveals its complete linear `TraceChain`.

## 5. User Interface & Workflow

The Daily Field Debrief Studio is situated directly between Evidence and Findings in the primary navigation:

$$\text{Overview} \longrightarrow \text{Field Intake} \longrightarrow \text{Evidence} \longrightarrow \mathbf{\text{Daily Debrief}} \longrightarrow \text{Findings} \longrightarrow \text{Lessons} \longrightarrow \text{Recommendations} \longrightarrow \text{QA Review} \longrightarrow \text{Brief}$$

### 5.1 Debrief History Timeline (`DebriefHistory.tsx`)
- Displays all debriefs recorded for the active study, sorted in **reverse chronological order** (most recent date first, falling back to creation timestamp).
- Search and filter bar enables real-time filtering by date, site name, attendee, or keyword across reflection contents and priorities.
- Each debrief card displays:
  - Header: ID badge (`DBR-001`), formatted date, attendee list.
  - Summary badges: `X sources`, `Y observations`, `Z priorities`, `N sites`.
  - Excerpt snippets: *What surprised us*, *Emerging hypothesis*, and *Observed contradiction*.
  - Actions: **View Full Reflections →** and **✎ Edit**.
- Clean empty state with explanatory guidance and a clear call-to-action button: `+ Record First Field Debrief`.

### 5.2 Structured Reflection Form (`DebriefForm.tsx`)
- **Field Session Context**:
  - Session date picker (defaults to today).
  - Multi-site selector: buttons for all study scope sites with visual selection indicator (`✓ Site A`), plus custom site input. Empty selection defaults to study-wide.
  - Attendees field with comma-separated parser.
- **Guided Reflection Questions**:
  - ⚡ *What surprised us today?* (Required)
  - 🔁 *What patterns repeated?* (Required)
  - ⚖️ *What contradicted earlier information?* (With divergence note badge and non-mutation informational note)
  - ❓ *Which assumptions should we question?*
  - 🔍 *Where might researcher/team bias be influencing interpretation?*
  - 👥 *Whose perspective is still missing?* (Features an integrated, read-only **System Evidence-Gap Signal** from the Phase 2 gap detector displaying target stakeholder groups with zero recorded observations).
  - 💡 *What hypotheses are emerging?* (Highlighted amber card with explicit **Boundary Guardrail** notice).
- **Tomorrow's Action Priorities**:
  - Discrete string list manager: add new priorities with Enter key or button, edit existing priorities in-place, reorder or remove.
- **Linked Field Material (`RecordLinkSelector.tsx`)**:
  - Dedicated sub-tabs for **Sources** and **Evidence Observations**.
  - Date filter toggle (*"Show only session date (YYYY-MM-DD)"*) with instant record counter.
  - Search filter by ID, title, site, theme, or observation content.
  - Validation status badges displayed on evidence items for clear context.

### 5.3 Full Detail View (`DebriefDetail.tsx`)
- Complete view of the debrief record with formatted timestamp metadata (`Logged YYYY-MM-DD`, `Updated YYYY-MM-DD`).
- All 7 reflection questions displayed as distinct cards with semantic iconography and color coding.
- Checkable/ordered list of tomorrow's priorities.
- Linked Source records displayed as cards with direct metadata and drawer inspect triggers.
- Linked Evidence observations displayed with primary/secondary themes and true validation status badges (`Draft`, `Needs Review`, `Validated`).
- Direct action button: `Inspect in Drawer →` which opens the Traceability Drawer for the debrief.

## 6. Persistence & Storage Architecture

All debrief operations are backed by IndexedDB (`FieldLearningStudioDB` v1) via `src/lib/storage/studyStore.ts`:

- **Store name**: `debriefs`
- **Key path**: `["studyId", "id"]`
- **Indices**:
  - `by_study`: `studyId`
  - `by_date`: `["studyId", "date"]`

### Core Storage Functions
- `saveDebrief(debrief: DailyDebrief): Promise<void>`
- `getDebrief(studyId: StudyId, debriefId: DailyDebriefId): Promise<DailyDebrief | undefined>`
- `listDebriefs(studyId: StudyId): Promise<DailyDebrief[]>`
- `deleteDebrief(studyId: StudyId, debriefId: DailyDebriefId): Promise<void>`
- `assembleStudy(studyId: StudyId): Promise<FieldStudy | undefined>` (loads debriefs along with meta, sources, evidence, findings, lessons, and recommendations).

### Collision-Resistant ID Generation
`src/lib/idGenerator.ts` provides `getNextDebriefId(existingIds: string[])`:
- Inspects existing debrief IDs matching `^DBR-(\d+)$`.
- Determines the numerical maximum (`maxNum`).
- Returns `DBR-${String(maxNum + 1).padStart(3, "0")}`.
- Survives non-contiguous sequences caused by deleted debriefs or imported backups.

### Demo Template Protection
- Pristine demo cases (`community-bridges`, `school-nutrition`) have `isDemoCase: true`.
- In the Daily Debrief tab, demo cases render an amber **Reference Demo Case (Read-Only)** notification banner.
- Direct creation of debriefs is disabled in demo mode.
- A prominent button, **Create Editable Copy**, creates a full cloned study in IndexedDB (`isDemoCase: false`), preserves the pristine template, and immediately transitions the user into the editable study with debrief capabilities enabled.
