# Field Intake Studio Guide (v0.9 Phase 3)

## 1. Overview & Purpose

Field Learning Studio v0.9 Phase 3 replaces temporary single-note sandbox simulations with a persistent, local-first **Field Intake Studio**. It provides MEL practitioners, evaluators, and field researchers with a disciplined workspace to capture narrative field material, verify privacy safeguards, and extract discrete evidence observations linked to persistent sources.

### Core Architecture Principles

1. **Local-First Persistence**: All sources and evidence are saved directly into the client's IndexedDB (`FieldLearningStudioDB` v1) under scoped compound keys `[studyId, id]`. No data is transmitted to external servers or cloud databases.
2. **Provenance & Auditability**: Every evidence entry is explicitly parented by a source record (`sourceId`) and captures contextual metadata: collection date, site location, stakeholder group, collection method, collector identity, consent status, anonymization status, and sensitivity classification.
3. **Safety Heuristics Without Overclaiming**: The narrative scanner checks for common identifying patterns (emails, phone numbers, exact dates, names, sensitive safeguarding terms). When clean, it reports *"No automated warning detected"*—never falsely claiming content is "Safe" or "Fully Anonymized." When potential flags are detected, user confirmation is strictly required prior to saving.
4. **Observation vs. Interpretation Separation**: Raw observations (what was directly seen, heard, or recorded) are kept analytically separate from interpretations (what the observation might signify or imply). Interpretations never overwrite or disguise observations.
5. **No Automatic Findings Generation**: Extracting evidence creates draft observations (`validationStatus: "Draft"`, `revision: 1`). It does *not* automatically generate findings or recommendations. Findings emerge through subsequent triangulation, sensemaking, and human validation.

## 2. Safe Human-Readable ID Generation (`src/lib/idGenerator.ts`)

Field entities require memorable, human-readable identifiers (`SRC-001`, `EV-001`, `FND-001`, etc.) for traceability diagrams, brief exports, and audit logs.

### The ID Collision Problem
Naive implementations using `items.length + 1` cause immediate collisions when:
- An item is deleted from the sequence (e.g. deleting `SRC-002` causes the next item to also be assigned `SRC-002`).
- Studies are merged or imported with non-contiguous sequences.

### Deterministic Solution
`src/lib/idGenerator.ts` inspects all existing IDs for a target prefix, extracts their numeric components via regular expression (`^PREFIX-(\d+)$`), finds the maximum numerical value (`maxNum`), and returns `maxNum + 1` zero-padded to at least three digits:

```typescript
export function getNextHumanReadableId(
  existingIds: string[],
  prefix: string,
  padLength: number = 3
): string {
  const regex = new RegExp(`^${prefix}-(\\d+)$`);
  let maxNum = 0;

  for (const id of existingIds) {
    const match = id.match(regex);
    if (match) {
      const num = parseInt(match[1], 10);
      if (!isNaN(num) && num > maxNum) {
        maxNum = num;
      }
    }
  }

  const nextNum = maxNum + 1;
  return `${prefix}-${String(nextNum).padStart(padLength, "0")}`;
}
```

Convenience wrappers:
- `getNextSourceId(existingSources)` -> `SRC-xxx`
- `getNextEvidenceId(existingEvidence)` -> `EV-xxx`
- `getNextFindingId(existingFindings)` -> `FND-xxx`
- `getNextLessonId(existingLessons)` -> `LES-xxx`
- `getNextGoodPracticeId(existingGoodPractices)` -> `GP-xxx`
- `getNextRecommendationId(existingRecs)` -> `REC-xxx`
- `getNextDebriefId(existingDebriefs)` -> `DBR-xxx`

## 3. Privacy & Safety Scanner (`scanNarrativeSafety`)

Field notes frequently contain sensitive stakeholder identities or safeguarding incidents that must not be mishandled.

### Detection Heuristics
`src/lib/sandboxParser.ts` exports `scanNarrativeSafety(text: string)` which returns:
```typescript
{
  hasWarning: boolean;
  warnings: string[];
}
```

Heuristics scanned:
- **Phone Numbers**: International formats, 10-14 digit sequences, dashed numbers.
- **Email Addresses**: Standard email regex patterns.
- **Specific Dates**: Formatted dates that could identify a specific interview day.
- **Personal Identifiers**: Terms like "Mr.", "Mrs.", "Dr.", "named", "called", followed by capitalized names.
- **Sensitive Topics & Safeguarding**: Keywords such as "abuse", "bribe", "violence", "threat", "assault", "confidential", "minor", "secret".

### Responsible UI Feedback
- **When clean**: Green badge reading *"No automated warning detected"*. Explanatory label: *"Automated scan found no obvious PII patterns. Always verify consent and anonymization manually."*
- **When triggered**: Amber warning banner listing specific detections. Saving is disabled until the practitioner checks the confirmation box: *"I confirm this narrative complies with safeguarding protocols and contains no unauthorized identifiable personal data."*

## 4. Source Capture Form (`SourceCaptureForm.tsx`)

Captures the full narrative record along with provenance metadata:
- **Title**: Descriptive summary of the encounter (e.g., *"Interview with Community Health Worker"*).
- **Collection Method**: Dropdown populated from study scope (`Key Informant Interview`, `Focus Group Discussion`, `Direct Observation`, `Document Review`, `Community Meeting`, `Survey / Questionnaire`).
- **Date**: Fieldwork execution date.
- **Site**: Location / site identifier selected from `study.scope.targetSites` or custom input.
- **Stakeholder Group**: Target group selected from `study.scope.targetStakeholderGroups` or custom input.
- **Collector Name**: Optional field team member name.
- **Consent Status**: `Written`, `Oral`, `Not Required / Public Source`, `Restricted / Unclear`.
- **Anonymization Status**: `Anonymized`, `Pseudonymized`, `Identifiable / Restricted`.
- **Sensitivity Level**: `Low`, `Medium`, `High`.
- **Raw Narrative**: Narrative text field supporting direct typing or pasted field logs.

When saved, `saveSource(study.id, newSource)` writes atomically to IndexedDB and automatically activates the source for observation extraction.

## 5. Observation Capture Form (`ObservationCaptureForm.tsx`)

Enables granular evidence extraction from an active source record.

### Workflow & Text Selection
1. The active source narrative is presented in a readable reference box.
2. The user can select/highlight text inside the narrative and click **"Use Selection"** to prefill the raw observation.
3. The user documents:
   - **Raw Observation**: What was directly observed, heard, or documented in the field.
   - **Analytical Interpretation**: What this observation might mean in relation to project objectives, assumptions, or community dynamics.
   - **Primary Theme**: Evaluative theme (e.g., Access, Coordination, Quality, Equity).
   - **Secondary Theme**: Optional secondary cross-cutting theme.
   - **Evidence Strength**: Initial manual rating (`High`, `Medium`, `Low`).
   - **Sensitivity Flag**: `None`, `Low`, `Medium`, `High`.
4. Observation is saved to IndexedDB (`saveEvidence`) with initial lifecycle metadata:
   - `validationStatus: "Draft"`
   - `revision: 1`
   - `createdAt: Date.now()`
   - `updatedAt: Date.now()`

## 6. Source History & Switcher (`SourceHistory.tsx`)

Located on the left sidebar of the Intake Studio:
- Displays all captured sources for the current study.
- Displays metadata chips: date, method, stakeholder, and sensitivity level.
- Displays the count of extracted evidence observations linked to each source.
- Allows switching active source with a single click to continue extracting observations from an earlier interview.
- Includes a "+ New Source" button to clear selection and open the intake form for the next encounter.

---

## 7. Integration with Analytical Engine & Existing Tabs

When working inside a local editable study:
1. `adaptFieldStudyToDemoCase(currentStudy)` transforms the normalized IndexedDB entities into the active projection consumed by the **Evidence Matrix**, **QA Review**, and **Learning Brief**.
2. Extracted observations immediately appear in the **Evidence Tab** as draft evidence items.
3. In the Evidence Tab, the triangulation engine computes the study-aware **Evidence Support Profile**:
   - Multiple observations from the same source count as **1 independent source** (`SingleSourceDependency` gap detected if claimed alone).
   - Observations across different methods and stakeholder groups expand the triangulation tier from `Emerging` to `Partially Supported` or `Strongly Supported`.
4. Read-only demo cases ("Community Bridges", "School Nutrition") display a banner prompting the user to clone into an editable study before capturing narrative notes, preserving the demo fixtures in pristine condition.
